# CalibriAI — MVP Development Specification

## 0. Роль

Ты выступаешь как Senior Full-Stack Developer и Tech Lead проекта CalibriAI.

Твоя задача — спроектировать и реализовать простой рабочий MVP, а не строить полноценную enterprise-систему.

Главный принцип проекта:

> Сначала рабочий продукт, потом усложнение.

Не добавляй функциональность, которой нет в этом документе.

Если видишь хорошую идею для будущего — зафиксируй её в `FUTURE.md`, но НЕ реализовывай.

---

# 1. Продукт

## Название

**CalibriAI**

Название отсылает к птице-калибри — маленькому и быстрому разведчику.

Рабочее позиционирование:

> **CalibriAI — персональный AI-рекрутер для поиска работы.**

## Главная задача

Пользователь хочет утром за несколько минут получить список релевантных вакансий с HH.ru вместо самостоятельного просмотра большого количества вакансий.

CalibriAI должен:

1. получить вакансии с HH.ru;
2. сохранить их локально;
3. определить, какие вакансии уже были получены ранее;
4. отправить новые вакансии в OpenAI API;
5. проанализировать их относительно профиля пользователя;
6. показать краткую сводку;
7. дать пользователю удобный интерфейс карточек;
8. позволить поставить Like / Reject;
9. для понравившейся вакансии открыть HH.ru;
10. по запросу пользователя сгенерировать персонализированное сопроводительное письмо.

# 3. Что входит в MVP

## Обязательно

### Поиск вакансий HH

* настройка поискового запроса;
* параметры поиска;
* получение вакансий;
* сохранение в PostgreSQL;
* определение уже известных вакансий.

### AI-анализ

Для каждой новой вакансии:

* соответствие навыкам;
* соответствие опыту;
* оценка зарплаты;
* общий Score;
* плюсы;
* минусы;
* red flags;
* краткое объяснение;
* итоговая рекомендация.

### UI

* настройки;
* запуск поиска;
* прогресс анализа;
* сводка;
* карточки вакансий;
* история решений;
* просмотр вакансии;
* генерация сопроводительного.

### Резюме

* загрузка нескольких резюме;
* выбор активного резюме;
* использование выбранного резюме при AI-анализе и генерации письма.

### История

* понравившиеся вакансии;
* отклоненные вакансии.

### AI usage

Сохранять:

* модель;
* количество input tokens;
* количество output tokens;
* примерную стоимость;
* время запроса.

# 4. Что НЕ входит в MVP

Не реализовывать:

* автоматическую отправку откликов;
* авторизацию;
* нескольких пользователей;
* Deep Research;
* исследование компаний;
* отзывы сотрудников;
* новости компаний;
* Knowledge Base;
* RAG;
* embeddings;
* обучение модели;
* сложный Recommendation Engine;
* несколько AI-агентов;
* Redis;
* RabbitMQ;
* Kafka;
* микросервисы;
* Kubernetes;
* LangChain;
* CrewAI;
* AutoGen;
* LlamaIndex;
* автоматический ежедневный scheduler;
* Telegram-бот;
* LinkedIn;
* другие источники вакансий.

HH.ru — единственный источник вакансий в MVP.

# 5. Технологический стек

Использовать:

## Frontend / Backend

**Next.js + TypeScript**

Не создавать отдельный Python backend.

Использовать возможности Next.js для server-side логики и API.

## Database

**PostgreSQL**

## ORM

**Drizzle ORM**

## UI

* Tailwind CSS
* shadcn/ui

Использовать shadcn/ui только там, где он действительно упрощает интерфейс.

## AI

OpenAI API.

API key хранится только на сервере.

Frontend никогда не получает API key.

## Infrastructure

Docker Compose.

# 6. Принцип архитектуры

Не строить сложную многослойную enterprise-архитектуру.

Предпочтительная структура:

```text
Next.js
│
├── UI
│
├── Server Actions / API
│
├── Business Logic
│
├── HH integration
│
├── OpenAI integration
│
└── Database
        │
        ▼
   PostgreSQL
```

При этом код должен быть логически разделен.

Например:

```text
src/
  app/
  components/
  lib/
    hh/
    openai/
    db/
    services/
  types/
```

Не смешивать:

* UI;
* работу с БД;
* OpenAI;
* HH;
* бизнес-логику.

Но не создавать отдельные абстракции только ради абстракций.

# 7. Конфигурация

Использовать `.env`.

Минимум:

```text
DATABASE_URL=
OPENAI_API_KEY=
OPENAI_MODEL=
```

API key никогда не должен попадать:

* в frontend;
* в client component;
* в git;
* в логи.

Добавить `.env.example`.

---

# 8. Настройки поиска

Создать страницу `/settings`.

Пользователь должен иметь возможность задать:

* поисковый запрос HH;
* зарплату от;
* регион;
* удаленную работу;
* опыт;
* количество вакансий.

Не нужно жестко ограничивать набор параметров, если HH API предоставляет дополнительные полезные параметры.

Но интерфейс должен оставаться простым.

Настройки сохраняются в БД.

При следующем запуске используются последние сохраненные значения.

Пользователь может изменить настройки и снова запустить поиск.

---

# 9. Получение вакансий

Создать отдельный модуль HH integration.

Не смешивать его с AI.

Задача модуля:

1. выполнить поиск;
2. получить вакансии;
3. нормализовать данные;
4. вернуть стандартную структуру вакансии.

Сохранять в БД как минимум:

* HH vacancy ID;
* URL;
* название;
* компания;
* зарплату;
* регион;
* описание;
* требования;
* обязанности;
* дату публикации;
* дату первого получения;
* исходные данные HH, если это полезно для повторного анализа.

---

# 10. Дедупликация

HH vacancy ID является основным идентификатором вакансии.

Если вакансия уже существует:

* не создавать новую запись;
* не запускать повторный AI-анализ автоматически.

Если вакансия новая:

* сохранить;
* поставить статус `NEW`;
* добавить в очередь текущего анализа.

---

# 11. Статусы вакансии

Использовать простую модель.

Минимум:

```text
NEW
ANALYZING
ANALYZED
LIKED
REJECTED
```

Не усложнять state machine.

---

# 12. AI-анализ

Для каждой новой вакансии выполнить AI-анализ.

Важно:

### AI должен анализировать ВСЕ новые вакансии.

Не делать предварительную фильтрацию обычным кодом.

Причина:

HH не всегда корректно или полно предоставляет:

* требования;
* зарплату;
* формат работы;
* технологии;
* другие важные параметры.

AI должен смотреть на полное описание вакансии.

---

# 13. Данные для AI

Передавать AI:

### Профиль пользователя

* выбранное резюме;
* навыки;
* опыт;
* желаемая зарплата;
* предпочтения поиска.

### Вакансию

* название;
* компания;
* зарплату;
* описание;
* требования;
* обязанности;
* формат работы;
* регион;
* другие доступные данные.

# 14. Результат AI

OpenAI должен возвращать строго структурированный JSON.

Пример:

```json
{
  "score": 87,
  "skills_match": 91,
  "experience_match": 84,
  "salary_match": 90,
  "recommendation": "high",
  "summary": "Краткая оценка вакансии",
  "pros": [
    "Хорошее совпадение по SQL",
    "Удаленный формат",
    "Интересный стек"
  ],
  "cons": [
    "Требуется опыт с конкретной технологией"
  ],
  "red_flags": [],
  "reasoning": "Объяснение итоговой оценки"
}
```

Не привязываться буквально к этому JSON, если при проектировании будет предложена более удачная структура.

Но результат обязательно должен быть типизированным и валидируемым.

---

# 15. AI Score

Score от 0 до 100.

Он должен учитывать минимум:

* навыки;
* опыт;
* зарплату;
* соответствие пользовательским предпочтениям.

AI должен объяснять оценку.

Нельзя показывать пользователю только:

> 87/100

Должно быть понятно:

> Почему 87?

---

# 16. Вероятность интервью / оффера

В MVP можно добавить:

* interview_probability;
* offer_probability.

Но AI обязан понимать, что это **эвристическая оценка**, а не статистически подтвержденная вероятность.

Не создавать видимость математической точности.

В UI обозначить это как AI estimate.

---

# 17. Объяснимость

Каждая рекомендация должна содержать:

### Почему подходит

Например:

* совпадает стек;
* релевантный опыт;
* подходит зарплата;
* подходит формат работы.

### Что смущает

Например:

* недостаток опыта;
* неизвестная технология;
* зарплата ниже ожиданий.

### Red flags

Если их нет — явно показывать:

> Красных флагов не обнаружено.

* сохранить ошибку;
* продолжить остальные;
* показать количество ошибок после завершения.

# 22. Открытие HH

Кнопка `Открыть HH` должна открывать оригинальную вакансию в новой вкладке.

CalibriAI НЕ отправляет отклик автоматически.

Пользователь самостоятельно выполняет отклик на HH.

---

# 23. Генерация сопроводительного

После `Откликнуться` показать:

> Сгенерировать сопроводительное письмо

Не генерировать письмо автоматически при каждом Like.

Письмо создается только после явного действия пользователя.

---

# 24. Требования к письму

Письмо должно быть:

* персонализированным;
* основанным на реальном опыте пользователя;
* основанным на конкретной вакансии;
* основанным на информации о компании, если она есть в вакансии;
* естественным;
* коротким и содержательным.

Запрещены клише вроде:

* "Меня заинтересовала ваша вакансия";
* "Я хотел бы выразить свой интерес";
* "Буду рад стать частью вашей команды";
* "Уверен, что мой опыт будет полезен вашей компании".

Письмо должно звучать как написанное человеком.

AI НЕ должен:

* придумывать опыт;
* придумывать проекты;
* придумывать технологии;
* придумывать достижения;
* изменять даты;
* приписывать пользователю навыки, которых нет в резюме.

* загрузить несколько резюме;

Если извлечение документов становится отдельной сложной подсистемой — разрешается на первом этапе использовать вставку текста резюме вручную.

Главная цель — быстрее получить работающий MVP.

# 30. Повторный анализ

> Переанализировать

Не обязательно реализовывать полноценную версионность анализа на первом этапе.

Но старый анализ желательно не терять.

# 31. Ошибки

Все внешние операции должны корректно обрабатывать ошибки:

* HH недоступен;
* OpenAI недоступен;
* превышен rate limit;
* некорректный ответ AI;
* ошибка БД;
* некорректный файл резюме.

Ошибка одной вакансии не должна ломать весь процесс анализа.

---

# 32. OpenAI

Использовать официальный OpenAI API.

API key хранить только на сервере.

Все AI-запросы должны идти через один внутренний модуль:

```text
lib/openai/
```

Не вызывать OpenAI напрямую из React-компонентов.

AI-модель задается через `.env`:

```text
OPENAI_MODEL=
```

Сейчас при разработке использовать GPT-5.5-compatible model, указанную пользователем в конфигурации.

Не хардкодить конкретную модель в бизнес-логике.

---

# 33. Промпты

Промпты не должны быть разбросаны по React-компонентам.

Хранить их отдельно.

Например:

```text
prompts/
  vacancy-analysis.ts
  cover-letter.ts
```

Все промпты должны явно описывать:

* роль AI;
* входные данные;
* ограничения;
* требуемый JSON;
* запрет на выдумывание информации.

---

# 34. Без сложных AI-фреймворков

НЕ использовать:

* LangChain;
* CrewAI;
* AutoGen;
* LlamaIndex;

если нет абсолютно необходимой причины.

Для MVP достаточно прямого вызова OpenAI API.

# 43. Важное правило для Cursor

Не принимай самостоятельно решения, которые существенно меняют архитектуру или функциональность.

Если обнаруживается неоднозначность:

1. остановись;
2. опиши проблему;
3. предложи 2–3 варианта;
4. укажи плюсы и минусы;
5. попроси пользователя выбрать.

Не реализовывай спорное решение молча.

Для мелких технических решений, не влияющих на архитектуру или пользовательский сценарий, используй здравый смысл.

# 44. Еще одно важное правило

Не переусложняй.

Если задачу можно решить:

```text
одним сервисом
```

не создавай:

```text
три сервиса.
```

Если достаточно:

```text
одной таблицы
```

не создавай:

```text
пять таблиц.
```

Если достаточно:

```text
обычного SQL query
```

не создавай:

```text
repository factory abstraction.
```

Код должен быть понятен одному разработчику.
